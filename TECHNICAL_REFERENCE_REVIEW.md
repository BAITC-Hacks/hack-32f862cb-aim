## Решение для нашего проекта

Использовать как референс устройства прогнозного компонента и тестов. Основу OptiStock сохраняем собственной: Python/FastAPI, React, PostgreSQL, Docker; адаптеры IEK и Systeme Electric, корректировка спроса, расчёт поставок по датам, версии заказов и согласование. Код и модели референса в наш проект не перенесены.

Проект демонстрирует цепочку «прогноз → проверка остатка → текстовое объяснение → запись решения менеджера». Его текущий расчёт не покрывает обязательные требования нашего кейса: совместный учёт источников, восстановление упущенного спроса, обработку разовых клиентских покупок и полноценные заказы по поставщикам.

## Что полезно

- **Единый контракт признаков при обучении и прогнозировании.** Порядок 38 признаков зафиксирован, проверяется обработка неизвестных значений и недостаточной истории. Для нас важен этот принцип, а состав признаков определяется нашими данными. [Признаки][features], [подготовка][preprocessing].
- **Временные признаки используют прошлые наблюдения.** Есть лаги и скользящие окна со сдвигом, тесты исключения текущего спроса. Это полезный образец проверок на использование будущей информации. [Тесты подготовки][prep-tests].
- **Рекурсивный многодневный прогноз.** Следующий шаг получает предыдущие предсказания; предусмотрен календарь будущих бизнес-факторов. Это один кандидат для сравнения на истории, а не доказанно лучший подход для наших SKU. [ForecastEngine][forecast], [тесты][forecast-tests].
- **LLM объясняет вычисленные числа.** Основной расчёт детерминирован, при недоступности Gemini предусмотрено шаблонное объяснение. Для нас объяснение также должно опираться на сохранённый результат расчёта. [Конвейер][agent].

## Ограничения и конкретные проблемы

| Наблюдение в коде | Последствие для OptiStock |
| --- | --- |
| Заказ при дефиците: `ceil((прогноз − остаток) × 1.20)`. Срочность определяется порогом дефицита 50 единиц. `horizon_days` в этой функции используется для описания | Нет расчёта срока новой поставки, ETA входящих партий, резерва, MOQ, кратности и календаря. Добавка 20% применяется к дефициту, а не выводится из ошибки спроса/срока. Источник: [inventory][inventory] |
| Вход и обучение требуют готовый `Demand`, цены, скидки, промо, цены конкурентов и другие розничные признаки; неизвестные SKU отклоняются | Наши продажи не равны наблюдаемому полному спросу. Нужны отдельная оценка спроса, признаки из доступных данных и политика короткой истории/нового товара. Чужой обученный артефакт напрямую неприменим. Источники: [features][features], [preprocessing][preprocessing] |
| В v1 API `confidence_score` равен 0.91 при объяснении Gemini, иначе 0.78 | Это зависимость от источника текста, а не измеренная уверенность прогноза. Такое поле нельзя переносить. Источник: [routes][routes] |
| `expected_stockout_risk` рассчитывается из отношения остатка к точечному прогнозу | Это индикатор недостатка покрытия, а не откалиброванная вероятность дефицита. Источники: [routes][routes], [agent][agent] |
| Согласование принимает прогноз и рекомендованное количество из тела запроса; `forecast_id` необязателен. Запись не сверяется с сохранённой ревизией расчёта; весь JSON читается и перезаписывается | Нужны серверная рекомендация, транзакции PostgreSQL, версии заказов, автор действия и защита от повторного утверждения. Текущая запись допускает расхождение с расчётом и потерю обновления при конкуренции. Источники: [schemas][schemas], [routes][routes], [approval][approval] |
| Авторизация выключена по умолчанию; при включении используется общий API key, а роль приходит в `X-User-Role` | Владелец общего ключа сам выбирает роль. Для нашего приложения роли и области доступа определяются сервером по подтверждённой личности. Источники: [config][config], [security][security] |
| `/api/v1/products` возвращает `P0001…P0020`, а `VALID_PRODUCT_IDS` допускает `P001…P004`; проверка выполняется до нормализации | Каталог v1 и входной контракт прогноза несовместимы для возвращаемых идентификаторов. Нужен сквозной тест «получить каталог → рассчитать выбранный товар». Источники: [routes][routes], [config][config] |
| Обучающий скрипт оценивает готовые строки тестового периода с лагами фактического прошлого спроса; рабочий многодневный прогноз рекурсивен | Такой тест не доказывает качество прогноза на весь горизонт закупки от одной даты. Нужна оценка тем же способом, каким система будет прогнозировать в эксплуатации. Источники: [train][train], [forecast][forecast] |
| `models/README.md` указывает WAPE 17.0537%, R² 0.7361; отчёт — WAPE 12.1769%, R² 0.8551; API отдаёт константу `accuracy=0.855` | Документы не согласованы. R² нельзя представлять как процент правильных прогнозов. Нужны измерения, связанные с версиями модели, данных, горизонтом и датами проверки. Источники: [карточка модели][model-card], [отчёт][evaluation], [config][config] |
| FastAPI и Streamlit запускаются в одном контейнере; API — фоновый процесс, ожидание фиксированные 2 секунды. PostgreSQL в этом решении нет | Этот deployment не реализует выбранную нами архитектуру. Нужны отдельные роли сервисов, readiness, постоянное хранилище, миграции и контролируемый жизненный цикл workers. Источники: [Dockerfile][docker], [start.sh][start] |

Дополнительно: наличие 14 строк истории не доказывает наличие 14 последовательных дней. Валидация проверяет сортировку, дубли и число строк, но не непрерывность календаря; лаги основаны на позициях наблюдений. Для наших транзакционных выгрузок сначала нужна корректная агрегация по дням и различение «нет продаж», «нет выгрузки» и «не было наличия». [Валидация][validation], [признаки][features].

## Что закрепляем в OptiStock

1. `ForecastModel` остаётся заменяемым компонентом. XGBoost можно проверить как кандидата после подготовки спроса; выбор зависит от результата на IEK/Systeme Electric, а не от чужого README.
2. Каждый прогноз фиксирует `dataset_id`, дату среза, горизонт, версию подготовки спроса, контракт признаков и версию модели. Сырые продажи, поправки и прогноз хранятся раздельно.
3. Историческая проверка воспроизводит доступность данных на дату расчёта, включая сезонность, корректировки и внешние факторы. При многодневном рекурсивном прогнозе внутрь горизонта не подмешивается будущий фактический спрос.
4. Оценка включает ошибку и смещение прогноза по сегментам, а также последствия для закупки: дефицит, запас и частоту заказов. Сравнение ведётся при одинаковых MOQ, сроках и допущениях о поставках.
5. Интервал прогноза и вероятность дефицита выводятся только при наличии соответствующей методики и проверки калибровки. При отсутствии такой проверки показываем метод, качество данных и индикатор риска без произвольного процента.
6. Числа в объяснении берутся из неизменяемой рекомендации. Утверждение адресует сохранённую ревизию заказа; LLM не определяет права и не подменяет расчёт.
