# OptiStock

Автоматический расчёт заказов поставщикам для пополнения склада — решение одного кейса «Электрокомплект», HackAlem AI. Менеджер перестаёт собирать заказ вручную в Excel: агент проверяет данные, выделяет регулярный спрос, учитывает остатки и поставки в пути, рассчитывает потребность и готовит объяснимые черновики по поставщикам.

**Основной экран: `/agent` (Procurement agent).** Менеджер проверяет риски, изменяет количество с причиной, утверждает заказ и скачивает CSV. Закупки автоматически не утверждаются и поставщикам не отправляются.

Работаем с 12 XLSX из материалов кейса: 3 909 товаров IEK / Systeme Electric. Это реальные файлы задания, а не подтверждённые текущие данные компании. Недостающие условия задаются явным сценарием. Синтетический Demo workspace обозначен отдельно.

## Для жюри: проверка за несколько минут

1. Запустить проект по одной из инструкций ниже. Открыть **Procurement agent**.
2. При первом запуске нажать **Загрузить материалы кейса**; для своих файлов использовать **Импорт Excel** с форматом IEK/Systeme. Дождаться завершения импорта.
3. Выбрать набор данных, поставщика/категорию, срок поставки, цикл, страховой запас и рост. Нажать **Запустить агента**.
4. Проверить этапы, показатели, вкладки **Требуют внимания** и **Разовые всплески**. Нажатие на SKU открывает числовое объяснение и источники.
5. Нажать **Проверить заказ**, изменить количество с причиной, сохранить и нажать **Approve order**, затем **Export CSV**. Закрыть и снова открыть страницу: расчёты и заказы сохранены в PostgreSQL.

Проверенный исходный сценарий: 491 позиция к пополнению (IEK 335, Systeme 156), 162 риска дефицита, 241 поправка по товарам в 231 уникальном документе у 190 SKU. Импорт и работа агента — 25,5 с в одном локальном замере. Полный браузерный тест с правкой, утверждением и экспортом также выполнен. Доказательства и ограничения: [VERIFICATION.md](VERIFICATION.md), [CASE_EVIDENCE.md](CASE_EVIDENCE.md). [Трёхминутная демонстрация и текст для сдачи](JURY_GUIDE.md).

## Быстрый запуск на Windows без Docker

Требуются Python 3.12+, Node.js 24 и установленные бинарники PostgreSQL в `C:\Program Files\PostgreSQL\…\bin`. Проверено с Python 3.13 и PostgreSQL 18.6.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m pip install --no-deps -e .
Push-Location frontend
npm.cmd ci
Pop-Location
.\.venv\Scripts\python.exe scripts/local_dev.py
```

Открыть **http://127.0.0.1:5173/agent**. Скрипт создаёт отдельный кластер в `var/local/postgres`, базы `optistock` и `optistock_test`, применяет миграции и запускает API, worker, frontend. Системная PostgreSQL-служба и существующие базы не изменяются. Порты: 5435 / 8000 / 5173. Логи и PID — `var/local/`; повторный запуск сохраняет данные.

Локальный ключ хранится на сервере в `var/local/api-key`; браузер обращается через dev proxy без получения ключа. Этот режим включается только локальным `.env.local`, проверяет origin/host и не включается в production-сборку. Если ранее выбран Demo workspace, на странице агента нажать **Подключить локальный сервер**. Для Docker и внешних API используются персональные ключи через Settings.

## Технологии и архитектура

React 19, TypeScript strict, Vite, Recharts; Python/FastAPI, Pydantic, openpyxl; PostgreSQL, SQLAlchemy и Alembic. Очередь задач находится в PostgreSQL, отдельный worker выполняет импорт и расчёт. API выдаёт результаты React-интерфейсу. Исходные файлы хранятся по SHA-256; каждый план фиксирует параметры, объяснения и версии обязательств.

Агент — исполняемый workflow из проверяемых инструментов: проверка → очистка → расчёт → риски → черновики. LLM не генерирует закупочные количества. Результат, журнал агента и черновики публикуются одной транзакцией; повторы защищены идемпотентностью и lease/token. Утверждение — отдельная операция менеджера с проверкой роли и ревизии.

Проект разработан с AI-агентом **Codex**, включая реализацию и автоматические проверки. Внешние платные API, OpenAI/NVIDIA-ключи и GPU для запуска не нужны. Публичная deployed-версия пока отсутствует; адрес выше — локальный. Репозиторий команды: [BAITC-Hacks/hack-32f862cb-aim](https://github.com/BAITC-Hacks/hack-32f862cb-aim).

## Запуск в Docker

Требуются Docker с Compose и Python 3 для генерации локального `.env`.

```bash
python3 scripts/configure.py
docker compose up -d --build
docker compose ps
```

`configure.py` создаёт случайные пароли, не перезаписывая существующий `.env`. Сервисы: PostgreSQL 17, миграции Alembic, FastAPI, отдельный worker и React frontend через Nginx. База и файлы сохраняются в volumes. Frontend слушает `127.0.0.1:5173`, API — `127.0.0.1:8000`, PostgreSQL — `127.0.0.1:5435`.

- Swagger: <http://localhost:8000/docs>
- React frontend: <http://localhost:5173>
- API health: <http://localhost:8000/health/live>
- БД и миграции: <http://localhost:8000/health/ready>

Создать административный ключ локального демо (выдаётся один раз):

```bash
mkdir -p var
docker compose exec -T api optistock create-key --name demo-admin --role admin > var/admin.key
chmod 600 var/admin.key
```

В Swagger нажать **Authorize** и ввести содержимое `var/admin.key`. Ключи хранятся в БД только в виде SHA-256; роль задаёт сервер. Роли: `viewer`, `planner`, `approver`, `admin`. Для другого пользователя создать отдельный ключ с другим именем. Отзыв: `docker compose exec api optistock revoke-key --name demo-admin`. Ключи и `.env` исключены из git.

## Полный демонстрационный сценарий

Папки `IEK/` и `Systeme electric/` включены в репозиторий и содержат по шесть исходных тестовых файлов задания. Compose подключает их только для чтения; Docker-образ не содержит Excel. Дополнительные выгрузки не требуются.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock
.venv/bin/pip install --no-deps -e .
.venv/bin/python scripts/demo.py
```

Скрипт через HTTP импортирует комплект, ждёт worker, рассчитывает план, создаёт черновики, сохраняет правку с причиной, утверждает и скачивает CSV в `var/`. Отчёт: `var/demo-summary.json`. Это демонстрационное утверждение тестовых заказов; поставщикам ничего не отправляется. Повторный импорт не создаёт дубликат набора. Повтор демо создаёт новый план с учётом уже утверждённых заказов; отмена заказа через API освобождает обязательство.

## API

Все `/api/v1/*` требуют `Authorization: Bearer <key>`. Все POST/PATCH требуют `Idempotency-Key`: повтор с тем же телом возвращает прежний результат, другое тело с тем же ключом — `409`. Для нового действия нужен новый ключ. Идентификаторы — UUID; количества рекомендуется передавать десятичными строками.

| Метод и путь | Результат |
| --- | --- |
| `POST /api/v1/datasets/sample` | Импорт 12 файлов; срез по умолчанию 2026-09-22 |
| `POST /api/v1/datasets/upload` | Multipart: `supplier` (`iek`/`systeme`), `as_of`, `files`; 1–12 XLSX |
| `GET /api/v1/datasets/{id}` | Состояние, состав и сводка набора |
| `GET /api/v1/jobs/{id}` | Этап, попытки и ошибка/результат |
| `POST /api/v1/jobs/{id}/retry` | Повторить неудачную задачу |
| `GET /api/v1/items?dataset_id=…` | Поиск, поставщик, категория, пагинация |
| `GET /api/v1/items/{id}` | Месячная история, источники и предупреждения |
| `GET /api/v1/items/{id}/transactions` | Исходные операции с пагинацией |
| `POST /api/v1/plans` | `dataset_id`, `scenario`; возвращает `plan_id` и `job_id` |

Начальный сценарий: поставка 30 дней, пересмотр 30 дней, страховое покрытие 14 дней, рост 0%. Параметры изменяемы и ограничены схемой. `supplier` и `category` ограничивают выборку. Складской охват — объединённый тестовый сценарий поставщика, без заявления о согласованном отдельном складе.

`category_safety_days` задаёт покрытие по исходным кодам категорий, например `{"1": 21, "7": 7}`; без словаря применяется общее `safety_days`. Значения категорий не объявляются ABC без расшифровки. Товары без месячной истории получают `insufficient_data`, а не статус достаточного запаса.

## Расчёт и ограничения

- Месячные продажи — основной ряд; транзакции не прибавляются к нему. Крупные документы корректируют только месяцы с согласующимися итогами. Повторяющиеся крупные покупки консервативно сохраняются. Клиентская идентификация не имитируется.
- Сезонность — нормированный профиль завершённых лет из отдельного файла, с пометкой о неподтверждённых единицах. Тренд применяется при согласии сравнений за 3 и 6 месяцев; рост сценария учитывается отдельно.
- Stockout оценивается по нулевым месячным снимкам как сценарное приближение. Поправки и предупреждение сохраняются; метод можно отключить.
- Неизвестный текущий запас заменяется последним снимком либо нулём согласно настройке. Пропуски продаж трактуются как ноль только при включённой явной настройке. Неизвестные MOQ/кратности используют видимые значения сценария.
- Поступления учитываются по датам: поздняя поставка не компенсирует ранний дефицит. Упущенные до новой поставки продажи не превращаются в backlog.
- Заказ округляется по MOQ, кратности и единицам закупки. Для отмеченных в источнике кабельных бухт используется видимый коэффициент сценария, 305 м по умолчанию.
- Утверждённые заказы входят в следующие расчёты. Устаревший план нельзя утвердить после изменения обязательств этому поставщику.

Это детерминированная модель MVP; её точность на будущих продажах не доказана. LLM не требуется; произвольных процентов уверенности нет. Экспорт — CSV, совместимость с конкретной обработкой 1С не заявляется.

## Эксплуатация MVP

Очередь находится в PostgreSQL: `FOR UPDATE SKIP LOCKED`, ограниченные попытки, lease, отдельный процесс задачи, token перед публикацией. Данные результата и статус успеха фиксируются одной транзакцией; частичный набор не становится готовым. API и worker перезапускаются независимо. Compose рассчитан на один узел, не является HA-кластером.

```bash
docker compose logs --tail 100 api worker
docker compose restart api worker
docker compose exec -T db pg_dump -U optistock -d optistock -Fc > var/optistock.dump
```

Вместе с dump БД сохранять volume `documents`: там исходные XLSX, контрольные суммы которых находятся в БД. `docker compose down` сохраняет данные; `docker compose down -v` удаляет их. Для внешнего размещения нужны HTTPS proxy, закрытый PostgreSQL-порт, резервное копирование с проверкой восстановления и персональные ключи. API/worker работают без root, с read-only root FS и лимитами ресурсов.
