# Обзор данных IEK и Systeme Electric

Уточнение пользователя: это полный тестовый комплект, новых данных не будет. Пробелы ниже являются ограничениями сценария, а не блокерами разработки. Их обработка реализуется через явные настройки и предупреждения; актуальное описание — `MVP_IMPLEMENTATION.md`.

Проверка: 23 сентября 2026 года. Прочитаны все 12 XLSX и их листы, проверены заголовки, число записей, ключи сопоставления и выбранные расчётные формулы. Исходные Excel не изменены. Это анализ исходных данных, не готовая реализация и не полная сверка всех числовых значений.

| Ежемесячные остатки | 2 853 уникальных кода | 701 уникальный код |

Строки с кодом не обязательно являются валидными продажами: в динамике встречаются разные типы документов и отрицательные количества. Все строки динамики с кодом имеют склад «Алматы». Ежемесячная история охватывает январь 2024 — сентябрь 2026 (33 месяца). Сентябрь нельзя считать закрытым месяцем без уточнения даты среза.

Даты в динамике IEK: 20.07.2023–22.09.2026; Systeme Electric: 18.01.2023–22.09.2026. Название «2025–2026» не описывает полный диапазон дат внутри файлов.

## Схемы и связи

- Основной ключ объединения: поставщик + строковый код 1С. Сохранять ведущие нули, подчёркивания и кириллицу. Артикул поставщика хранить отдельно.
- Динамика обеих компаний: Дата, Номер, Документ, Код, Номенклатура, Ед., Склад, Количество. Полей клиента и цены здесь нет. Номер документа не является ID клиента.
- Ежемесячные продажи: широкая таблица по месяцам; для расчёта преобразовать в строки товар–месяц. Исключить строки/колонки «Итого». Не прибавлять динамику к месячной истории: это потенциально два представления одних операций.
- У Systeme Electric в месячных продажах есть артикул и кратность; в отдельном MOQ кратности могут отличаться от этой колонки. Например, у `030200128_` в продажах 0, в MOQ 1. Нужен явный приоритет источника.
- IEK: заголовки остатков прямо указывают «нач. остаток». Это не остаток на 22 сентября и не число дней наличия. У Systeme Electric в месячной таблице смысл момента замера не подписан, его нужно уточнить.
- IEK, файл пути: количества в отдельных колонках поставок; в заголовках ожидаемые даты 30.09, 01.10, 10.10 и 15.10.2026. Нормализовать в строки товар–поставка–дата–количество.
- Systeme Electric, `Товар в пути...`, лист `TDSheet`: категории 2026, СС реал, история продаж, показатели роста/сезонности, отдельные складские показатели, общий остаток, резерв, свободный остаток, заказ, поставка «СЭ в пути 24.09». Год этой поставки выводится из контекста файла, а не из самой ячейки. Категории обозначены числами; расшифровка нужна отдельно.

## Найденные проблемы

1. **Ошибка окна среднего в Systeme Electric:** `TDSheet!AP3 = SUM(AC3:AO3)` включает сентябрь 2025 — сентябрь 2026, то есть 13 месяцев, при заголовке «Сумма последние 12 мес». `AQ3 = AP3/12`. Проверена эта строка; распространение дефекта на весь столбец отдельно не проверялось. Пересчитывать своё явно заданное окно, учитывая неполный сентябрь.
2. **Неоднозначное название сезонности:** `AS3 = SUM(AC3:AE3)/SUM(Z3:AB3)-1` с IFERROR, то есть относительное изменение квартальных сумм, а не обычный сезонный множитель. `AR3` — относительное изменение июнь–август 2026 к июнь–август 2025. Нельзя использовать эти величины как взаимозаменяемые коэффициенты.
3. **Отрицательные количества:** в динамике IEK 115 отрицательных строк, Systeme Electric 302. Не брать модуль автоматически; уточнить возвраты/корректировки и типы документов. Отрицательные значения есть и в месячных продажах.
4. **Дубли ключей:** IEK MOQ — код `270400035_` встречается дважды; в пути — семь кодов встречаются дважды. До объединения проверить, одинаковые ли это записи или разные позиции/поставки. Обычный merge может размножить строки.
5. **Неполное покрытие:** из месячных продаж IEK 7 кодов отсутствуют в остатках, 702 в MOQ, 379 в файле пути. У Systeme Electric все 554 кода есть в остатках и MOQ, но 85 отсутствуют в файле пути. Отсутствие записи не равно подтверждённому нулю.
6. **MOQ IEK:** 15 строк не имеют положительного числового значения в поле минимальной отгрузки. Минимальная партия и кратность — разные ограничения; правило округления требует подтверждения.
7. **Единицы:** в пути IEK есть товары с примечанием «закупаются бухтами, садятся метражом». Нельзя вычитать бухты из остатков в метрах без коэффициента пересчёта.
8. **Сезонность:** книги содержат агрегаты продаж, расчётные коэффициенты и прогнозные значения. Например, IEK отдельно помечает коэффициенты октября–декабря 2026 как прогноз. Единицы исходных агрегатов нужно подтвердить; не смешивать их с количественной историей SKU. Дублирующиеся листы не считать независимыми источниками.

## Покрытие требований кейса

- Продажи, история остатков, сезонность, входящие поставки и MOQ: источники найдены.
- Текущий свободный остаток и категории: найдены у Systeme Electric для части ассортимента; у IEK сопоставимой текущей ведомости среди файлов нет.
- Устойчивый рост: можно оценивать по очищенной истории. Внешний план прироста не выделен отдельным источником; расчётный исторический рост не равен бизнес-плану.
- Точные stockout-интервалы: не найдены. Месячные снимки допускают лишь приближённую оценку и не доказывают непрерывное отсутствие товара.
- Крупные покупки одного клиента: нет обезличенного ID клиента. До получения поля можно оценивать аномалии по документам/товарам, явно обозначив ограничение.
- Сроки новых заказов поставщикам: отдельного справочника нет. Даты уже ожидаемых поступлений его не заменяют.
- Совместимый формат загрузки заказов в 1С: образец не предоставлен.

## Решения для будущей реализации

Стек пользователя: Python + FastAPI; React (предлагается TypeScript + Vite); PostgreSQL и Docker с первого этапа, проект для промышленной эксплуатации. Подробности — `BACKEND_ARCHITECTURE.md`.

Раздельные адаптеры файлов двух поставщиков → общая модель данных → проверка качества → прогноз/пополнение → объяснения, корректировка и экспорт. Использовать данные обоих поставщиков, сохраняя происхождение каждого поля и дату среза. Не маскировать отсутствие обязательных данных нулями. Любые допущения по сроку поставки, категориям и stockout должны быть видимыми и изменяемыми.

Перед расчётом сверять месячные итоги с детализацией; поправки по документам применять только при согласовании сумм. Клиентский ID не имитировать; stockout и текущий запас оценивать с пометкой, сроки/MOQ/кратность/пересчёт единиц/рост задавать сценарием. Экспортировать документированный CSV без заявления о подтверждённой совместимости с конкретной обработкой 1С. Дополнительные данные не запрашиваются.
