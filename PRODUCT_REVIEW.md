# OptiStock: разбор концепции и сравнение с аналогами

Ниже сохранён разбор концепции до реализации. Текущий backend и уточнённый объём MVP описаны в `MVP_IMPLEMENTATION.md`; утверждения об отсутствии кода относятся к моменту первоначальной проверки.

Дата: 23 сентября 2026 года. Название OptiStock подтверждено пользователем. Изучены все 10 страниц предоставленного файла `вв.pdf`; документ содержит структуру проекта, методы расчёта, интерфейсы, инструменты AI-ассистента и заявленные статусы работ. Сравнение продуктов основано на официальных публичных описаниях, а не на испытании их систем.

## 1. Продукт

OptiStock — система планирования закупок для дистрибьютора электротехнической продукции. Она преобразует продажи, остатки, ожидаемые поставки и условия поставщиков в объяснимый план пополнения, который менеджер проверяет, корректирует и утверждает.

Рабочий цикл: актуальные данные → оценка регулярного спроса → прогноз → рекомендации по сроку/объёму → сценарии → согласование → передача утверждённого заказа → контроль исполнения и пересчёт.

Первые адаптеры: IEK и Systeme Electric. Подтверждённый стек: Python/FastAPI, React, PostgreSQL, Docker. Детали эксплуатации — `BACKEND_ARCHITECTURE.md`. Streamlit и локальный файловый workflow из PDF не заменяют этот стек.

## 2. Что из PDF переносим в проект

- Расчётное ядро отделено от интерфейса и LLM; одинаковый контракт для реальных и синтетических данных.
- Раздельные компоненты импорта, аномалий, stockout, сезонности, прогноза, расчёта заказа, объяснения, экспорта и исторической проверки.
- Проверка повторяемости крупных покупок, чтобы не исключить регулярного оптового покупателя.
- Сохранение исходного и очищенного ряда, журнала поправок и числового объяснения.
- Иерархия сезонности и отдельная модель-кандидат для редкого спроса; выбор и настройки подтверждаются на истории.
- Карточка товара с исходными продажами, поправками и прогнозом; список рекомендаций по поставщикам; сценарии «что если».
- AI-ассистент получает числа через инструменты, объясняет рекомендации и запускает сценарии с правами текущего пользователя. Утверждение заказа остаётся действием менеджера.
- Проверки пяти обязательных требований на контролируемых данных.

## 3. Что требует исправления или подтверждения

| Положение PDF | Вывод для OptiStock |
| --- | --- |
| Стр. 2–3: Streamlit и CSV-файлы как основа конфигурации | Сохраняем смысл модулей, реализуем через FastAPI/React, версионированные настройки PostgreSQL и Docker |
| Стр. 3: изменение знака количества в 2025 году | Проверить распределение знаков по периодам и типам документов; не вводить преобразование по году без сверки месячных итогов |
| Стр. 3: загрузчик «решает» отсутствие текущего остатка IEK | Из имеющихся месячных снимков нельзя достоверно восстановить текущий остаток без поступлений и других движений; нужны дополнение или видимая оценка |
| Стр. 4: ноль на начале/конце месяца означает заниженный спрос всего месяца | Это лишь признак возможного дефицита. Возможны продажа последней единицы в конце месяца, отсутствие спроса или пополнение внутри месяца. Коррекция — по подтверждённому интервалу либо явно маркированному сценарию |
| Стр. 4: обрезать только избыток крупного заказа | Подходит как кандидат робастной обработки; не всегда достаточно для отделения проектных закупок. Нужно хранить разовую потребность отдельно, с возможностью подтверждения менеджером |
| Стр. 4: группа определяется по коду 1С, брендовая сезонность в тенге | Смысл префиксов кода и денежные единицы не подтверждены словарём. Используем подтверждённые группы; денежный сезонный профиль не выдаём за количественный без проверки |
| Стр. 4: уровень × сезон × рост × план прироста | Уровень должен соответствовать выбранной сезонной нормировке. Рост и план могут описывать одно изменение; требуется режим замены или дополнительного роста с периодом действия |
| Стр. 5: A всегда имеет больший страховой запас, чем C | Категория задаёт целевой уровень обеспеченности/политику; абсолютный запас зависит также от спроса, срока и неопределённости. Значения «Категория 2026» не считаем автоматически ABC |
| Стр. 5 и 7: вероятность дефицита через нормальное приближение | Не универсальное правило для всех SKU. Требуется проверка распределения и калибровка; для редкого спроса сравнивать сценарную/эмпирическую оценку. Без такой проверки выводить индикатор риска без выдуманного процента |
| Стр. 5: пример 38 × 1,10 с ростом +8% даёт около 42 | При одновременном применении получается 45,144, а не 42. Объяснение и таблица обязаны использовать одну расчётную запись |
| Стр. 5: CSV «код, артикул, количество» совместим с 1С | Совместимость устанавливается по целевой конфигурации/обработке 1С, единицам, поставщику и формату обмена; название файла её не доказывает |
| Стр. 5: скрыть последние шесть месяцев для backtest | Исключить использование будущих данных также при очистке, сезонности, выборе модели и настройке параметров. Оценивать несколько временных срезов; Excel baseline должен быть описан и воспроизведён |
| Стр. 7: статистические методы уже лучше сложных моделей | Это проверяемая гипотеза, а не установленный результат; чисел backtest и кода в текущем репозитории нет |
| Стр. 9: заказ ×50 меняет рекомендацию менее чем на 10% | Это предложенный тест из PDF, не точный порог исходного ТЗ. При исходном заказе 0 относительный процент неопределён; нужны абсолютный допуск и заранее заданный сценарий |
| Стр. 10: часть модулей готова | В текущей рабочей директории найдены документы и Excel, но перечисленных Python-модулей нет. Готовность из PDF не подтверждена локальным кодом и тестами |

Клиентский ID в полученных Excel отсутствует. Номер накладной не заменяет его. Требование исходного кейса — обезличенные данные на входе; добавление хеширования в загрузчик не является основанием принимать неразрешённые персональные данные. Если вводится устойчивый псевдоним клиента, его ключ и область стабильности должны позволять связать покупки между разрешёнными выгрузками, не попадая в LLM и экспорт.

## 6. Продуктовые решения

### Обязательный фундамент первой рабочей версии

Пять требований ТЗ; PostgreSQL/FastAPI/React/Docker; проверяемый импорт; сведения об ограничениях данных; прогноз и объяснение; ручная корректировка; версии заказов/согласование; экспорт; роли; аудит; мониторинг и проверка восстановления. Ограничения рабочего запуска — в BACKEND_ARCHITECTURE.md.

### Следующий приоритет по аналогам

- **Календарь пополнения:** дни заказа, время отсечения, доступные даты доставки, целевой горизонт и свежесть источников. Автоматически рассчитывать рекомендации, а отправлять только утверждённую ревизию.
- **Очередь проблем:** товар закончится до поступления, поставка просрочена, MOQ создаёт избыток, входной файл устарел, нет нужных полей. У проблемы есть причина, владелец и предлагаемое действие.
- **Контроль заказа:** заказано → подтверждено поставщиком → отгружено → частично получено → закрыто/отменено. Изменение количества или ETA запускает пересчёт затронутых товаров.
- **Сценарии:** например, срок поставки 20/40 дней или дополнительный рост спроса. Сравнение количества заказа, покрытия и дефицита; стоимости — только при достоверной цене.
- **Качество:** мониторить ошибки прогноза, смещение, частоту ручных правок и их результат. Автоматически не считать каждую правку менеджера правильной обучающей меткой.

### Возможности с отдельными требованиями к данным

- ABC по выручке/марже требует цен/маржи и периода; нельзя складывать метры и штуки по всему ассортименту для денежного ABC. XYZ — отдельная оценка изменчивости, не замена исходной категории.
- Альтернативный поставщик требует соответствия товаров, предложений, цен, сроков и доступности. Наличие папок двух брендов не означает взаимозаменяемость SKU.
- Перемещения между складами требуют запаса по каждой локации, спроса, сроков и стоимости перемещения. Полный multi-echelon нельзя доказать на общей выгрузке Алматы.
- Оптимизация бюджета, вместимости и минимальной суммы заказа требует стоимости, объёма/веса и условий. При отсутствии цены нельзя показывать денежную «экономию».
- Цветные зоны запаса могут показывать риск дефицита/достаточность/избыток, но не заявляются копией закрытых алгоритмов LEAFIO. Числовые границы выводятся из нашей политики и прогноза.

## 7. Как доказать полезность

1. Временной backtest с доступными на тот момент данными: MAE, WAPE при ненулевом знаменателе, смещение; разрезы поставщика и поведения спроса. Не скрывать нулевые знаменатели и не выводить единую «точность 95%» без определения метрики.
2. Сравнение с описанным текущим Excel-процессом и сезонным базовым прогнозом. Найденную ошибку окна 13/12 отметить отдельно; результат исправленного baseline не выдавать за исходную практику менеджера без согласования.
3. Симуляция закупок на зафиксированных допущениях: незакрытый спрос, средний запас и излишек по товару/единице, частота заказов, выполнение MOQ. Итоги маркировать как модельные, а не доказанную экономию компании.
4. После пилота — фактическое время менеджера на заказ, доступность товаров, подтверждённые сроки/полнота поставок и финансовый результат при наличии учётных данных.

Рабочая формулировка ценности: «OptiStock помогает закупщику электротехнического дистрибьютора отделить регулярный спрос от проектных покупок, учесть дефицит и поставки и утвердить объяснимый заказ на данных 1С». Это позиционирование для проверки на пилоте, не утверждение превосходства над конкурентами.
