# OptiStock: подготовка к HackAlem AI

Актуальный этап: разработка backend MVP на полном имеющемся тестовом комплекте. Инструкции запуска — `README.md`, реализованный объём — `MVP_IMPLEMENTATION.md`. Исторический план подготовки ниже не означает ожидание новых данных.

## Текущий кейс

Название продукта подтверждено пользователем: **OptiStock**. Концепция и сравнение с аналогами — `PRODUCT_REVIEW.md`.

Выбран кейс ТОО «Электрокомплект»: автоматизация формирования заказов поставщикам. Предыдущий кейс Beeline отменён и не относится к реализации. Подробный разбор требований: `LOGISTICS_CASE.md`. Общий план ниже применяется с учётом этого разбора. Пользователь зафиксировал промышленную направленность проекта: Python + FastAPI, React, PostgreSQL и Docker сразу. Архитектура и условия выпуска — `BACKEND_ARCHITECTURE.md`.

## Уточнения из общих правил и инструкции участникам

Прочитаны оба PDF целиком (по 2 страницы): «Правила зачета участия» и «Инструкция_для_участников_HackAlem_AI».

- Инструкция отводит 5 часов на обязательные функции и проверку сквозного сценария. Точное время старта и дедлайна в этих документах не указано.
- Решаем один кейс. При разработке требуется использовать AI-агента; отдельного требования встроить LLM в продукт инструкция не устанавливает.
- Проект должен быть создан в рамках хакатона, каждый участник должен внести личный вклад.
- Итоговый код должен находиться в командном GitHub-репозитории, выданном платформой. API-ключи публиковать запрещено.
- После отправки кода нужно отдельно открыть страницу треков, выбрать кейс, нажать «Сдать решение», заполнить название и описание. Обновления разрешены до дедлайна.
- README: название, проблема и пользователь, реализованные функции, сквозной сценарий, технологии, архитектура, установка и запуск, воспроизводимый пример проверки, данные и интеграции, ограничения, ссылка на развёрнутую версию при наличии. Описывать только подтверждённую реализацию.
- Документ активации OpenAI и NVIDIA упомянут, но пока не предоставлен. Вложенный промпт для README — образец, а не отдельное поручение немедленно переписать README.

Правила присутствия: собственный отсканированный бейдж; вернуться до старта; после старта не пересаживаться и не менять сектор; личные выходы суммарно до 60 минут, каждый с уведомлением стюарда и сканированием на выходе/входе. Весь последний час находиться на площадке (экстренный выход до 5 минут — только с разрешения стюарда). Не уходить до официального завершения. Стюарды и свидетели не участвуют в разработке, по техническим вопросам обращаться к ментору.

Предлагаемое распределение 5 часов после старта:
1. 0:00–0:30 — данные, схема, распределение задач и критерии приёмки.
2. 0:30–2:30 — расчёт спроса и заказа, сезонность/рост, stockout и разовые заказы.
3. 2:30–3:30 — интерфейс, объяснения, корректировка и экспорт по поставщикам.
4. 3:30–4:15 — проверки пяти обязательных требований и сквозного сценария.
5. 4:15–5:00 — исправления, README, отправка кода и сдача на платформе с запасом до дедлайна.

## Когда появится задание

Сохранить исходную постановку и правила, затем уточнить:

1. Кто пользователь, какую конкретную проблему решаем и как он решает её сейчас?
2. Что обязательно показать и сдать: репозиторий, работающий сервис, видео, презентацию?
3. Когда дедлайн и по каким критериям оценивают решение?
4. Какие данные доступны, можно ли использовать внешние модели и сервисы?
5. Есть ли обязательные технологии, лимиты API, бюджет и ограничения на заранее подготовленный код?
6. Какие роли и навыки есть у участников команды?

## Выбор решения

Для каждой предложенной темы записать пользователя, боль, доступные данные и один демонстрируемый результат. Сравнить варианты по соответствию критериям жюри, доступности данных, реализуемости за отведённое время и наглядности демо.

Выбрать один основной пользовательский сценарий. Зафиксировать измеримый результат и список функций, которые не входят в MVP. Самый рискованный элемент — доступ к данным, качество модели или интеграцию — проверить первым.

## Порядок разработки

1. Проверить правила, доступы, данные и минимальный вызов нужного API.
2. Собрать сквозной сценарий: ввод → обработка → результат.
3. Проверить результат на нескольких реалистичных примерах, включая сложные и ошибочные входы.
4. Добавить понятные состояния загрузки, ошибок и отсутствия результата.
5. Подготовить запуск, демонстрационные данные, README и короткую презентацию.
6. Оставить время на репетицию и исправления; остановить добавление функций перед сдачей.

## Технические решения после выбора темы

- Выбирать стек по опыту команды и требованиям задачи; не добавлять отдельный backend, БД или очередь без конкретной необходимости.
- Если нужна генеративная модель, держать ключи на сервере, конфигурацию — в переменных окружения, в репозитории — только `.env.example` без секретов.
- Если ответы должны опираться на документы, показывать источники и проверять ответы на тестовых вопросах. Поиск по документам добавлять только при наличии такой задачи.
- Для внешних API предусмотреть таймауты, понятные ошибки и ограничения расходов.
- Хранить небольшой набор проверочных примеров: вход, ожидаемый результат или критерий качества, фактический результат.
- Демонстрационные или заранее сохранённые ответы явно обозначать; не выдавать их за живую обработку.

- [ ] В репозитории нет ключей, токенов и приватных данных.
- [ ] README описывает установку, переменные окружения, запуск и ограничения.
- [ ] Демо воспроизводится по короткому сценарию.
- [ ] Есть резервная запись или скриншоты с честным пояснением режима демонстрации.
- [ ] Материалы и ссылки соответствуют формату сдачи.

## Сценарий выступления

Пользователь и проблема → существующий неудобный процесс → один живой сценарий решения → полученный результат → роль AI → ограничения и следующий шаг. Длительность подстроить под регламент.
